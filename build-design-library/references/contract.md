# Product and Project Contract

## Read authority in order

1. repository and directory instructions
2. decision records and approved product specifications
3. package manifests, source code, generated contracts, and tests
4. current research with an active status
5. historical notes
6. external references

The higher source wins a conflict. Record the conflict. Stale or binding text changes only with authorization.

## Discover project policy

Find rules for:

- product terminology and roles
- data privacy and fixture content
- authentication and authorization
- external services and credentials
- accessibility and supported devices
- dependencies, copied code, and licenses
- generated files and public assets
- worktrees, branches, commits, and cleanup
- decision storage and issue tracking
- development, gallery, test, and verification commands

Record each authority path and its effect. Quote exact text only when wording controls the work.

## Map the product

Map the approved product from the user inward:

1. users and roles
2. outcomes and journeys
3. applications and routes
4. pages and panels
5. states and transitions
6. components and foundations
7. data and service contracts

Include signed-out, permission, loading, empty, filtered-empty, stale, disconnected, partial, error, success, and confirmation states when reachable.

## Inspect the shipped system

Read the actual system:

- theme and token sources
- rendered fonts and font loading
- logos, icons, illustrations, and public assets
- UI exports and primitive base
- exact installed versions and lockfiles
- source and license records
- fixtures and scenario builders
- gallery entry points
- application routes and API clients
- generated API schemas
- component and browser tests
- startup and cleanup scripts

A change to shipped tokens or established behavior is an owner decision, routed through the project decision process.

## Discover runtime capabilities

Inspect the current runtime registry and tool list. Record whether these capabilities exist:

- design craft
- interaction psychology
- design QA
- live browser measurement
- repository scouting
- external research
- reference-product capture
- implementation
- integration
- complexity review
- test hardening
- independent acceptance

Record the actual skill, role, or tool name, or `missing`. The user selects models; route work by available capability and ownership boundary.

## Prepare owner choices

Each material choice contains:

- the question
- authoritative constraints
- valid options
- consequence and change cost for each option
- recommendation with evidence
- decision location

Silence keeps the choice open.

## Contract completion

The contract is complete when it names:

- every authority path
- approved scope and exclusions
- users, roles, pages, journeys, and meaningful states
- shipped foundations and reusable assets
- implemented and proposed data routes
- required modes and device classes
- source and license process
- supported startup and browser route
- targeted and full verification commands
- runtime capability status
- integration owner
- open owner choices

A missing authoritative full verification command blocks completion.
